# PP-533 load test

Does a single check from an instructor still come back within 10 s (NFR3) while a
500-row batch is draining through the same detector? This folder answers that as
an experiment: measure the service time, write a prediction, ramp the load until
the app breaks, then run the headline test at a chosen rate.

The measured runs go against the **AWS deployment**, before go-live. A local
breaking point would measure the laptop, not the product (see
[`EXPERIMENT_LOG.md`](EXPERIMENT_LOG.md), Entry 1). Locally, this folder only runs
a smoke test that proves the harness works.

Design: `docs/superpowers/specs/2026-10-22-pp533-load-test-design.md` (phases,
breaking-point rules) and `docs/superpowers/specs/2026-10-24-pp533-aws-load-test-design.md`
(the AWS target), both local copies, gitignored. Results: [`RESULTS.md`](RESULTS.md).

## Local smoke test (harness check)

Needs Docker (with Compose v2) and bash. On Windows use Git Bash.

```bash
bash apps/loadtest/run.sh smoke
```

This starts a fresh, disposable stack (`prompt-patrol-loadtest`: api, worker, the
e2e stub detector, Postgres on tmpfs, LocalStack) with **no host ports**, so it
can run next to the dev stack. It sends 20 single checks and one 20-row batch,
then tears everything down with `down -v`, even on Ctrl-C. It takes a few minutes.
Pass = exit 0 and `status: ok` in the run's `meta.json`. Run it before every AWS
session. It is a plumbing check, never a result: `render` leaves stub runs out.

Every other phase refuses to run against the local stack.

## Phases (AWS)

Run each phase for **desklib** (the production model).

| # | Phase | Answers |
|---|---|---|
| 1 | `calibrate` | Service time S (median of 100 serial checks). Prints capacity C = 1/S and the 9 ramp rates |
| 2 | *(no command)* write the prediction in `EXPERIMENT_LOG.md` | What do we expect before measuring? |
| 3a | `ramp-idle` | Where does latency start to climb (onset) and where does it break, single checks only? (~21 min) |
| 3b | `ramp-batch` | Same, while 500-row batches drain (~21 min + batch setup) |
| 4 | `headline-idle --rate R --runs 3`, `headline-loaded --rate R --runs 3` | PP-533 AC1–AC4 at the chosen rate R (req/min) |
| 5 | `freeze --rate R` | How long does `POST /api/batches` block the API's event loop? |
| 6 | after the `create_batch` fix: `freeze --variant async`, `headline-loaded --variant async --runs 3` | Before/after for the fix |
| — | `render` | Rebuild `figures/` and `RESULTS.md` from `results/` (no stack needed) |

How `run.sh` targets AWS (load generator, session cookie, WAF allow rule) is
defined in the AWS spec and is not built yet.

Choosing R (Phase 4): the suggested default is about 50% of the under-batch
breaking point from Phase 3b, plus a "realistic classroom" rate. Write the reasoning
in the `rate-choice` block of `RESULTS.md` and in the log.

Options: `--model baseline|desklib` (default desklib), `--rate PER_MIN`, `--runs N`,
`--variant sync|async` (default sync), `--service-time S` (otherwise taken from the
newest ok calibrate run for that model).

Exit codes: `0` passed, `99` k6 thresholds failed (a result, not a broken run),
`3` k6 passed but the run was flagged (`invalid`, `aborted`), `130` interrupted,
other = the run broke.

## Where things go

- `results/<UTC time>_<model>_<phase>/` — one directory per run, never deleted or
  overwritten: `meta.json` (settings, host, git SHA, `status`), `summary.json`,
  `requests.csv.gz` (every request), `batches.csv`, `k6.log`, `dashboard.html`
  (k6's dashboard, for poking around).
- A bad run is kept and flagged in `meta.json` (`status`: `invalid`, `aborted`,
  with `status_reason`); `render` lists it under "Excluded runs". Directories
  starting with `_` are ignored.
- `figures/` — PNG (300 dpi) + SVG, each with a footnote naming model, host and
  run ids.
- `EXPERIMENT_LOG.md` — `run.sh` appends one line per run; add your own notes
  (predictions, decisions, surprises) under `## Notes`.
- `RESULTS.md` — regenerated by `render`; text between `<!-- hand:… -->` markers is
  yours and survives every re-render.

Locally, k6's session token comes from a seeded dev session in the throwaway
database. It is never written to disk; `run.sh` checks the run directory for it
and marks the run `invalid` if it ever shows up.

**After each AWS session, commit** `results/`, `figures/`, `RESULTS.md` and
`EXPERIMENT_LOG.md`.
